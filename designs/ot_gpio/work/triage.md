# Failure triage

Failures: 3; analysed: 3. The designer decides; nothing was changed.

## 1. CHK-006: Disabled interrupts never assert o_intr_gpio. 196 fails = 40 in base.s1, 23 in base.s2, 40 in min.s1, 45 in straps_off.s1 and 48 in sync_off.s1 (the NNC_CHECK lines in each log). First fail at 300745000 ps.

**Most likely:** B_test_wrong

| Part | Content |
|---|---|
| Specification says | contract.json:404-416 (CHK-006): "At the D handshake (edge Ed) of a write to 0x4 (INTR_ENABLE) with o_d_error=0, shadow_en=data. For each i: if shadow_en[i]=0 and the edge is at least Ed+2 after the last INTR_ENABLE write ..., then o_intr_gpio[i]=0." The rules behind it only say what the output is, not when a write takes effect. CP-T1.8.6-04 (rules.json:5646-5651): "The output of the INTR_STATE register becomes the outgoing interrupt to the processor after masking (ANDing) with the value of INTR_ENABLE." CP-T1.8.4-03 (rules.json:5364-5369): INTR_ENABLE "enables/masks the output of INTR_STATE". Timing is given only by D-018, spec/gpio_Design_Specification.md:1165: "o_intr_gpio[i] equals INTR_STATE[i] AND INTR_ENABLE[i] except in the 2 cycles after either changes ... Lower bounds are not checked." D-004 (spec:1151) also says o_intr_gpio[i] is not checked "in the 4 cycles after INTR_ENABLE[i] is set to 1 when such an event may have been latched." No document says whether a register write takes effect at the A handshake or at the D handshake. |
| RTL does | The register write happens at the A handshake, not at the D handshake. tlul_adapter_reg.sv:152 a_ack = a_valid & a_ready. Line 155: wr_req = a_ack & Put*. Line 158: we_o = wr_req & ~err_internal. gpio_reg_top.sv:6315: intr_enable_we = addr_hit[1] & reg_we & !reg_error. prim_subreg.sv:63-64 loads q on wr_en, so reg2hw.intr_enable.q changes at the A-handshake edge Ea. prim_intr_hw.sv:96-101 registers intr_o <= status & reg2hw_intr_enable_q_i, so o_intr_gpio shows the new enable from edge Ea+2. The response is d_valid = outstanding_q (tlul_adapter_reg.sv:232) and is completed only when i_d_ready=1, so the D handshake Ed = Ea+1+stall. Take a write that sets INTR_ENABLE[i] from 0 to 1 while INTR_STATE[i]=1, under D back-pressure: from Ea+2 until Ed+1 the RTL drives o_intr_gpio[i]=1 while the checker's shadow_en[i] is still 0. The interrupt datapath itself (gpio.sv:950-972, prim_intr_hw.sv:62-72) is the standard Event type and uses state & enable as the spec requires. |
| Test does | Every failure falls inside test_chk_038_outstanding_backpressure (296285-316880 ns, sim.log:143-145) or test_regression_random (316880-383645 ns, sim.log:146-148). Both enable D-channel back-pressure: h.bp=True at test_ot_gpio.py:1484 and :1606, with bp_prob=0.25 and bp_max=10 (lines 244-245); i_d_ready is held 0 for 0..10 cycles (lines 336-346). Both send random PutFullData writes to INTR_ENABLE (wr_addrs at lines 1490 and 1525, issued at lines 1502 and 1537, and phase 2 at line 1631). They also write random values to the INTR_CTRL_EN_* / LVL* registers, which set INTR_STATE bits through level events, so enabling a bit with a latched state is common. The checker (nnc_chk_intr.sv) stores the request at the A handshake (lines 83-87). It updates shadow_en only at the D handshake: wr_ev = d_hs && eff_ok && eff_w4 && !o_d_error (line 66), applied at lines 91-93. It masks only the edge Ed (!wr_ev) and Ed+1 (settled=0) in chk006_ante (line 104), then asserts (o_intr_gpio & ~shadow_en)==0 (line 107). The window between Ea and Ed is not excluded. Failures come in runs of 1 to 9 consecutive 10 ns edges, for example 300745-300795 and 300835-300895 (sim.log:182-221). That matches stalls of up to bp_max=10 cycles. |
| B_test_wrong | For: The checker assumes INTR_ENABLE changes at the D handshake (nnc_chk_intr.sv:66, 91-93). With back-pressure, the A-to-D gap is not bounded, and the RTL commits the write at the A handshake (tlul_adapter_reg.sv:155-158). So an enabling write shows on o_intr_gpio before the shadow knows about it. Failures happen only in the two tests that use back-pressure (test_ot_gpio.py:1484, 1606), and the run lengths (≤9 edges) fit bp_max=10. In effect CHK-006 checks a lower bound on when an enable takes effect, which D-018 says is not checked (spec:1165). D-004 also excludes o_intr_gpio checks right after INTR_ENABLE[i] is set to 1 (spec:1151). The scoreboard in the same test passes, i.e. o_intr_gpio == INTR_STATE & INTR_ENABLE in steady state (test_ot_gpio.py:1616, all tests PASS sim.log:179), and CHK-007 and CHK-004 show 0 fails.<br>Against: The CHK-006 text in contract.json:413 states the D-handshake shadow explicitly, so the checker implements the plan as written. The plan, not only the SVA code, would need to change. Without a waveform, the claim that every failing edge lies between an enabling INTR_ENABLE write's A and D handshakes comes from timing, not from a trace. |
| A_rtl_wrong | For: If the design were required to apply a register write only when its response is accepted (D handshake), the RTL would be early. The checker also only sees o_intr_gpio[i]=1 where its model says the bit is disabled.<br>Against: No rule in rules.json or spec/gpio_Design_Specification.md says a write takes effect at the D handshake. The RTL is the stock OpenTitan adapter: the write commits at the A handshake (tlul_adapter_reg.sv:155-158), and d_valid follows one cycle later (line 232). The interrupt logic is the standard state & enable flop (prim_intr_hw.sv:100). Disabling writes take effect earlier than Ed+2, so they can never fail this check. Only enabling writes during a stall can fail, which points to a model timing problem, not a masking bug. |
| C_spec_unclear | For: The spec never says when a register write becomes effective relative to the TL-UL A and D handshakes. D-018 (spec:1165) measures 'the 2 cycles after either changes' without saying when the register 'changes', and its gpio/oe bound is measured from 'the response of the write'. Read that way, a D-handshake reference is defensible, and the gap is that the documents do not say what happens before the response.<br>Against: D-018 explicitly says 'Lower bounds are not checked', and D-004 explicitly exempts the cycles after INTR_ENABLE[i] is set to 1. Together these resolve the question against checking before the response, so the mismatch sits in how the checker models the timing. |
| Options | Fix the test/checker without weakening the property. In nnc_chk_intr.sv, treat the bits that a pending INTR_ENABLE write sets from 0 to 1 as 'in transition'. That window runs from the A handshake (a_hs && cur_w4, or pend_valid && pend_w4) until Ed+2. For example, mask o_intr_gpio[i] for i in (pend_data & ~shadow_en) while that write is outstanding, and for 2 edges after Ed. Bits that remain 0 in both the old and the new value must still be checked on every edge, so the check is not weakened for truly disabled bits. Alternatively, update shadow_en at the A handshake, which matches the RTL commit point, and keep the Ed+2 settle window, adjusting the d_error qualification because d_error is only known at D. Update the CHK-006 'behavior' text in contract.json:413 to match. Clarify the spec (optional): add to D-018 or D-004 that a register write may take effect at any time between its A handshake and its response, and that o_intr_gpio is not checked for bits being enabled in that window. Fix the RTL: not recommended. Nothing in the documents requires write effects to wait for the D handshake. Changing the stock tlul_adapter_reg would diverge from OpenTitan. |

## 2. CHK-008: Outputs held at zero during reset. 1 failure per run in all 5 runs (5 total), always at time 0 (NNC_FAIL CHK-008 @0, sim.log:181, min.s1.log:78). hits=0 in every run.

**Most likely:** B_test_wrong

| Part | Content |
|---|---|
| Specification says | D-016, spec/gpio_Design_Specification.md:1163 and rules.json:3768-3773 (GP-10-31): "While rst_ni = 0, o_d_valid, o_alert, o_alert_integ_fail, o_intr_gpio, o_gpio and o_gpio_en shall be 0". INT-RST-001 (spec:1017-1019, GP-2-05/GP-2-06): "rst_ni is the active-low reset, asserted asynchronously and released synchronously to clk_i ... While rst_ni is 0, every register holds its reset value". D-003 (spec:1150): o_gpio and o_gpio_en are 0 while rst_ni=0. contract.json:441: "This includes the first clock edge after rst_ni falls asynchronously." No document covers time 0, before rst_ni has ever been asserted (there is no power-on state). |
| RTL does | All output-driving flops are asynchronous-reset flops that are only reset by a negedge of rst_ni or by a posedge of clk_i while rst_ni=0. Examples: gpio.sv:859-861 (cio_gpio_q), 884-886 (cio_gpio_en_q); prim_intr_hw.sv:96-98 (intr_o); prim_alert_receiver.sv:255-259 (state_q <= InitReq); prim_alert_sender.sv:271-276 (prim_flop with ResetValue 2'b10, i.e. alert_n=1, alert_p=0). o_alert_integ_fail comes from combinational logic (prim_alert_receiver.sv:160-166, 245-249): integ_fail_o=1 whenever alert_sigint is set and state_q is not InitReq/InitAckWait. alert_sigint is the XNOR of alert_p and alert_n (prim_diff_decode.sv:219-222). At time 0, Verilator (2-state, zero-initialised, no X→0 edge) has not run any reset assignment. So alert_p = alert_n = 0, which gives sigint=1, and state_q is 0 rather than InitReq. o_alert_integ_fail can therefore be 1 at the first clock edge at time 0, before any reset assignment has run. After the first clock edge with rst_ni=0 the flops take their reset values and every listed output is 0. This is inferred from the code; the log does not say which output was non-zero. |
| Test does | The test starts the clock and then waits for RisingEdge, FallingEdge and RisingEdge in Env.start (test_ot_gpio.py:475-487) before Env.reset calls reset_dut (lines 489-501). reset_dut and start_clock live in nnc_cocotb, which is not in this directory. rst_ni is therefore not deliberately driven 1 then 0 before the first clock edges at time 0. In 2-state Verilator it reads 0, but no falling edge ever happens. The SVA (nnc_chk_reset.sv:43 posedge and :48 negedge) has no 'disable' or 'reset seen' qualifier and fires at the t=0 clock edge. The hit counter at nnc_chk_reset.sv:45 uses the condition `!(!rst_ni) && (!rst_ni)`, which is always false, so hits=0 in every run whether or not the check works. The test-level copy of the same check (_sample, test_ot_gpio.py:456-462) records no CHK-008 error in any test, and this copy only starts after Env.start (line 485). That includes test_chk_030_async_short_reset (lines 1218-1245), which checks the outputs at the first falling edge after an asynchronous reset assertion. All 26 tests PASS (sim.log:179). |
| B_test_wrong | For: There is exactly one failure per run, always at time 0, and never at any later reset (including the asynchronous 2-cycle reset in CHK-030 and the reset in test_regression_random line 1688). At t=0 no reset has been asserted: rst_ni has no falling edge in 2-state simulation, so the asynchronous-reset flops have not been reset yet. The contract talks about the edge 'after rst_ni falls'. The test bench does not start with rst_ni=1 followed by an asynchronous fall, and the checker does not wait for a real reset assertion. The hits counter at nnc_chk_reset.sv:45 can never count, which is a separate checker bug.<br>Against: The failing output is not printed, so the explanation through o_alert_integ_fail (or another uninitialised output) is inferred from the code, not observed. nnc_cocotb.reset_dut / start_clock and nnc_tb_top.sv are not provided, so it cannot be confirmed how rst_ni is driven at t=0. |
| A_rtl_wrong | For: Read literally, rst_ni is 0 at that edge and an output is non-zero. A design whose outputs are forced to 0 combinationally by !rst_ni, rather than by flop reset, would pass even at t=0.<br>Against: The RTL is standard OpenTitan with asynchronous-reset flops, which is the reset strategy the spec names (INT-RST-001, spec:1017). Outputs are 0 at every edge with rst_ni=0 after a real reset assertion, both in the SVA (no further fails) and in the test-level checks (CHK-030 passes). The t=0 state comes from the simulator's 2-state initialisation without a reset edge, and the RTL has no control over it. |
| C_spec_unclear | For: The spec defines outputs 'while rst_ni = 0' but says nothing about the state before the first reset assertion, or whether a rst_ni that starts at 0 counts as an asserted reset. The contract's 'first clock edge after rst_ni falls' suggests a fall is required, but this is not stated in the rules.<br>Against: Every rule assumes reset is asserted (asynchronously) by the test bench, which is the stimulus side. Requiring a well-defined assertion at start-up is a normal test-bench duty, not a spec gap that needs a design decision. |
| Options | Fix the test bench (preferred): drive rst_ni=1 at time 0, before or together with starting the clock, and assert it 0 asynchronously before the first rising edge, for example after a fraction of the period. The real falling edge then fires the asynchronous reset and the outputs are 0 at every checked edge, including t=0 if rst_ni is 0 there. Alternatively, in nnc_chk_reset.sv, start checking only after the first observed falling edge of rst_ni, or after the first clock edge processed with rst_ni=0. This is not a weakening, because before that no reset has been asserted. Also fix the hit counter at nnc_chk_reset.sv:45 (`if (!rst_ni) hits_CHK_008 <= hits_CHK_008 + 1;`) so coverage is reported. Before deciding, print which output was non-zero at t=0 (add the six values to the $display at lines 44 and 49) to confirm the root cause. Clarify the spec (optional): state in D-016 that the reset checks apply from the first assertion of rst_ni and that the test bench starts with rst_ni=1 and then asserts it. Fix the RTL: not indicated. |

## 3. CHK-011: Test-bench stimulus legality monitor. 12685 fails, all in the two GpioAsyncOn=0 runs: min.s1 (GpioAsyncOn=0, GpioAsHwStrapsEn=0) with 6327 fails (min.s1.log:6589) and sync_off.s1 (GpioAsyncOn=0, GpioAsHwStrapsEn=1) with 6358 (sync_off.s1.log:6628). **Most likely:** B_test_wrong

| Part | Content |

| Specification says | INT-CLK-001, spec/gpio_Design_Specification.md:1010-1011 (GP-2-02, rules.json:1898-1903): "All TL-UL and strap inputs are sampled and all outputs change at its rising edge". INT-CLK-002, spec:1013-1015 (GP-2-04, rules.json:1954-1959): "With GpioAsyncOn = 0 there is no synchronizer, and the test bench shall change i_gpio only synchronously to clk_i, like the other inputs." | RTL does | Not involved. CHK-011 checks only the stimulus. The DUT outputs it reads (o_a_ready for rule a, o_d_valid/o_d_source for rule c) are used only in rules (a) to (e). The A channel is driven after await FallingEdge (lines 288, 307-316), i_d_ready likewise (lines 333, 346), and i_gpio for GpioAsyncOn=0 likewise: set_gpio docstring "GpioAsyncOn=0: synchronously right after the falling edge" (lines 524, 527-530). The checker samples the inputs at the negedge (nnc_chk_tlhost.sv:92-95, neg_in_q <= cur_in), before the cocotb writes made after that FallingEdge. At the next posedge it compares cur_in != neg_in_q (line 122) without any disable (line 123). So every edge after an input change fails. Examples: alternating a_data between DIRECT_OUT write data and 0 in normal_traffic (lines 614-621) gives fails every 20 ns at 6.12-6.86 us (min.s1.log:90-127), inside test_chk_016. | B_test_wrong | For: The plan constraint is explicit: inputs change 'only just after rising edges' (contract.json:488, and again in CHK-021 stimulus contract.json:677). The test bench does the opposite by design, driving after falling edges (test_ot_gpio.py:5, 288-316, 333-346, 524-530). Failures appear only in the configurations where (f) is active (GpioAsyncOn=0). They occur at the edges where an input changed, for example every 20 ns when a_data alternates in normal traffic. The test's own set_gpio docstring contradicts the CHK-021 stimulus text.<br>Against: Driving at the falling edge is a common, race-free way to apply synchronous stimulus. The DUT samples all inputs at the rising edge, so the RTL sees legal, stable values, and every functional test passes in the GpioAsyncOn=0 runs. The violation is against the plan's specific choice of drive edge, not against a hazard visible in the design. |
| C_spec_unclear | For: The spec only says 'synchronously to clk_i, like the other inputs' (spec:1013-1015) and that inputs are 'sampled ... at its rising edge' (spec:1010). Changing inputs half a cycle before the sampling edge is also synchronous. 'Just after rising edges' is a stricter choice made in the verification plan (contract.json:488), not stated in the gpio specification. The test-bench author read the spec as allowing falling-edge drive (test_ot_gpio.py:5).<br>Against: The contract, which is the binding verification plan, removes the ambiguity explicitly, and so does CHK-021's stimulus. | A_rtl_wrong | For: None found. This monitor checks the stimulus, not the DUT.<br>Against: Rule (f) checks only test-bench inputs. The fails depend only on GpioAsyncOn, which controls whether (f) is active, and the GpioAsyncOn=1 runs with identical traffic show 0 CHK-011 fails. |
| Options | Fix the test bench (matches the plan): when GpioAsyncOn=0, drive all inputs just after the rising edge instead of after the falling edge. That covers the A-channel fields and i_a_valid in TLHost._a_loop (test_ot_gpio.py:285-327), i_d_ready in _d_loop (329-346), i_gpio in set_gpio/gpio_pulse (521-547), i_strap_en (1594, 1599, strap_sequence) and the idle/reset values in Env.reset/reset_dut.
