## Open questions (the designer decides: `nnc answer <design> <n> "<decision>" --by <name>`)

1. Is the filter delay exactly 16 module clock cycles when the pin is an output, and does the input register reflect output changes only after that delay? Also, is the stable-input window restarted on any glitch? (GP-T2.2-05, GP-T2.2-06) — *The documents say the input must be stable for 16 module clock cycles and that with the filter on and the pin set to output, a change in output value reaches the input register with a delay. They do not say that the count restarts on a glitch. D-007 says the exact threshold is not checked; it only bounds the behaviour: a value held 12 cycles or less never appears, and one held 24 cycles or more appears within 24 cycles. The designer must define the exact count and the glitch-restart semantics.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-21T01:03:45+00:00): Not defined by the documents. D-007 applies: the exact count and whether a glitch restarts it are not checked; tests hold a new filtered value either at most 12 cycles (must not appear) or at least 24 cycles (must appear within 24 cycles). There is no pad model (INT-IO-002, D-021): DATA_IN follows i_gpio only, so output-to-input delay is not a case here.

## Questions answered by the documents

- In masked write, which half (upper/lower) is selected and how are the mask and data fields laid out? Does the quote define this? → MASKED_OUT_LOWER (and MASKED_OE_LOWER) controls bits 15:0 of DATA_OUT (DATA_OE). MASKED_OUT_UPPER (and MASKED_OE_UPPER) controls bits 31:16. In the register write, the upper 16 bits (31:16) are the mask and the lower 16 bits (15:0) are the data. A bit is updated only where its mask bit is 1. [T3.2.1:s2, T3.2.1:s4, T5.8:s2, T5.8:s3, T5.8:s4, T5.8.1:s1, T5.8.1:s2, T5.9:s2, T5.9:s3, T5.9.1:s1, T5.9.1:s2]
- Is the interrupt noise filter path (CTRL_EN_INPUT_FILTER) optional per input, and how does the 'MUST pass through filter' rule relate to it being optional? → Yes. The noise filter is optional and independently enabled per input through CTRL_EN_INPUT_FILTER. The 16-cycle filter applies to both DATA_IN and interrupt detection when enabled. 'All inputs go through the filter' therefore means each input passes through the optional filter stage, which is active only where its enable bit is 1. [T3.2.3:s3, T3.2.3:s4, T3.2.3:s5, T3.2.4:s12, T5.17:s2]
- Is the error response for a byte write to PER_PIN_IO_i a bus error response, and does it apply to every kind of access (e.g., a capability-checked access versus a plain write)? Also, what does a write of 16 bits or more that is not aligned to bytes 0-1 do? → A write narrower than the register's fields is rejected: a byte write to PER_PIN_IO_i returns an error (d_error=1) and has no effect, so a write must cover both bytes 0 and 1 (at least 16 bits). Hardware sees only the bus access, so the error is independent of any capability check; the capability must simply cover those two bytes. PER_PIN_OE_i and PER_PIN_INTR_CTRL_i accept byte writes. For the register tool, 8b or 16b writes that are not 4B-aligned also return an error. A 16-bit write at the wrong byte lane is therefore an error. [T4.4:s7, T4.4:s8, T4.4:s9, 10:s16, T1.4.1:s14, T1.4.1:s17, T1.4.1:s19, T1.4.1:s20]
- Registers list reset 'x' for PER_PIN_OE/INTR_CTRL fields but the note for indices 1..31 says reset default 0x0; which is correct? → The 'Reset default' line binds: PER_PIN_OE_i, PER_PIN_INTR_CTRL_i and PER_PIN_IO_i.data_out read 0 after reset. The 'x' in the field tables is overridden, and indices 1..31 follow GPIO[0] with reset default 0x0. [10:s6, T5.21:s5, T5.22:s6, T5.23:s2, T5.20:s4]
- Is the snapshot taken on the strap_en rising edge, on level high, or on a specific cycle, and how many cycles after the event do sampled_straps values become valid? → The snapshot is triggered by the low-to-high transition (rising edge) of strap_en_i, not by the level. The GPIO detects the transition on the first cycle strap_en_i is asserted after reset and samples the inputs one clock cycle later, storing them in HW_STRAPS_DATA_IN. The bound used by the verification is that the valid indications read 1 within 4 cycles after the edge. [T3.2.3.1:s2, T3.2.3.1:s3, T5.19:s4, 10:s11]
- Can a later strap_en assertion (for example after reset) trigger a new snapshot, given that behaviour after the event 'has no effect'? → Within one reset period, sampling occurs only once and later changes are not captured. After each reset the GPIO detects the transition again, so a new strap_en rising edge after a reset triggers a new snapshot. [T3.2.3.1:s2, T3.2.3.1:s4, T3.2.3.1:s5, T5.19:s1, 10:s11]
- What are the exact interrupt modes (rising, falling, level high/low) and the latency from detection to the interrupt event? → There are four modes per bit: rising edge (INTR_CTRL_EN_RISING), falling edge (INTR_CTRL_EN_FALLING), level high (INTR_CTRL_EN_LVLHIGH) and level low (INTR_CTRL_EN_LVLLOW). No exact latency is given. D-018 bounds it: INTR_STATE is set no later than 4 cycles after the event appears in DATA_IN, and o_intr_gpio equals INTR_STATE AND INTR_ENABLE except in the 2 cycles after either changes. Lower bounds are not checked. [T3.2.4:s6, T3.2.4:s7, T3.2.4:s8, T3.2.4:s9, 10:s21]
- Is the pass-through of GpioAsyncOn/GpioAsHwStrapsEn something to be checked (e.g. by elaboration), or only a configuration note? What is the observable behaviour for each value? → The two parameters are passed through unchanged from gpio to ot_gpio_nnc. Verification runs in the combinations the run set selects. GpioAsyncOn=1 instantiates 2-flop synchronizers on the inputs, so i_gpio may change at any time; 0 means no synchronizer and i_gpio changes only synchronously to clk_i. GpioAsHwStrapsEn=0 makes HW_STRAPS_DATA_IN read 0, with the valid and data outputs unchecked. GpioAsHwStrapsEn=1 samples straps as described in D-008. The documents do not call for an elaboration check. [1:s5, 1:s6, 1:s7, 1:s8, 2:s3, 2:s4, T5.19:s3, T5.19:s4, 10:s11, 10:s12]
- Which signals identify a ping request, and in which block should the 'never issued' property be checked? → A ping request is the receiver's ping_req_i assertion, which appears as a level change on alert_rx.ping_p/n towards the sender. The configuration states that ping requests are never issued. This property concerns the wrapper's alert receiver, which connects to gpio's alert sender. [1:s3, 1:s4, 5:s2, T1.3.3:s3, T1.3.3:s4]
- Which actor drives i_gpio and rst_ni (test bench vs. system), and are the INT-CLK-002 and GpioAsyncOn = 0 constraints environment assumptions rather than DUT checks? → The test bench drives i_gpio, which depends on nothing in the DUT. The test bench also resets the design. The INT-CLK-002 rule (with GpioAsyncOn=0, i_gpio changes only synchronously to clk_i) is a constraint on the test bench stimulus, an environment assumption rather than a DUT check. With GpioAsyncOn=1, i_gpio may change at any time. rst_ni is asserted asynchronously and released synchronously to clk_i. [6:s2, 2:s3, 2:s4, 2:s5, 10:s20]
- GP-2-02 says all outputs change only at the rising clk_i edge except for rst_ni; does that exception cover asynchronous reset assertion forcing outputs low immediately, and does i_gpio with GpioAsyncOn=1 pass through a synchronizer to outputs? → Yes. The edge-only rule has the exception of rst_ni's effect. While rst_ni is 0, the listed outputs are 0, and the rule is not applied in cycles where rst_ni is 0 or falls. With GpioAsyncOn=1 the inputs pass through 2-flop synchronizers before reaching DATA_IN, which adds delay, and D-018 bounds this by 4 cycles after the first rising edge when the filter is off. [2:s2, 2:s5, 2:s6, 10:s19, 1:s6, T3.2.3:s8, 10:s21]

The timing of equality affects any assertion. → o_gpio is DATA_OUT and o_gpio_en is DATA_OE. DATA_OUT is updated by the direct or masked write, and the masked write is applied by hardware without read-modify-write. The only timing stated is a bound: o_gpio and o_gpio_en equal DATA_OUT and DATA_OE no later than 2 cycles after the response of the write that changed them. Lower bounds are not checked, so a purely combinational path is not required. [6:s1, T3.2.1:s5, 10:s21]
- Is o_alert / o_alert_integ_fail a level or a pulse, and is it sticky until cleared? Latency from the alert event is not specified. → o_alert is a pulse: it is 1 for one clock cycle per alert handshake detected by the receiver, and it is not sticky. o_alert_integ_fail is the receiver's integ_fail_o and a correct sender never raises it (D-017: 0 whenever rst_ni=1). Latency: a write of 1 to ALERT_TEST.fatal_fault gives exactly one o_alert pulse no later than 16 cycles after the write response. After an accepted request with i_a_intg_flip=1, o_alert pulses within 16 cycles. [5:s2, 5:s3, 5:s4, 10:s13, 10:s20]

A correct device never makes it 1, and it shall be 0 in every cycle with rst_ni=1. [4.3:s1, 4.3:s2, 10:s20]
- Is a_user.rsvd and a_user.instr_type observable at the wrapper's ports, or only internally? This decides whether GP-4.1-02 and GP-4.1-03 can be checked every cycle from interface signals. → Only instr_type is tied to a port: i_a_instr=1 gives MuBi4True and 0 gives MuBi4False. a_user.rsvd is fixed to 0 inside the wrapper and has no port. The bit layout of a_user/d_user and the user-bit defaults are not checked. [3:s12, 4.1:s2, 10:s25]
- The integrity generator code is not part of the spec and the Bus Integrity Scheme section is not written. How should correct cmd_intg and data_intg be checked, and what does a rsp_intg check failure mean? → The test bench does not compute or check cmd_intg/data_intg. The wrapper's generator produces them, and the generator code and the Bus Integrity Scheme section are not part of the specification. i_a_intg_flip=0 means correct integrity and i_a_intg_flip=1 inverts bit 0 of cmd_intg. A rsp_intg check failure is reported as o_d_intg_err=1 (response integrity of the D-channel beat is wrong). A correct device never produces it, and it shall be 0 whenever rst_ni=1. [4.2:s1, 4.2:s2, 4.2:s3, 4.3:s1, 4.3:s2, 10:s20, T3.1.4:s1]
- Does 'repeated until reset' in GP-5-05 specify a repetition period, or only that o_alert pulses more than once? A write of 1 to ALERT_TEST.fatal_fault triggers only one alert event (exactly one o_alert pulse), so the bus integrity fault alert repeats while the ALERT_TEST path does not.
