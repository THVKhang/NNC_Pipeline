## Open questions (the designer decides: `nnc answer <design> <n> "<decision>" --by <name>`)

1. Which internal signals can be observed by the testbench (FSM states, reg_a_valid)? Several rules refer to internal state. (BR-5.3-02, BR-5.4-02, BR-5.4-04, BR-5.3-11) — *The spec names internal registers and FSM states but does not say which internal signals the testbench may observe (hierarchical access or probes). The designer must define the observable internal signal set.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-07T18:05:58+00:00): Black-box only: tests and checkers observe the top-level ports and nothing inside the DUT (REQ-VER-001 binds the checkers to the ports). Rules about internal registers and FSM states (BR-5.3-02, BR-5.4-02, BR-5.4-04, BR-5.3-11) are verified through their port-visible effects: request on channel A in the first Access cycle, a_valid held and channel A stable until a_ready, PREADY one cycle, next Setup accepted in the cycle after PREADY. The internal state itself is not_observable_at_interface.
2. How should an illegal parameter be reported at elaboration of the verification source set (error, fatal, or assertion), and which tool performs the check? (BR-8-09, BR-8-10) — *The spec says an illegal value is reported at elaboration of the verification source set (TEST-014 elaboration check). It does not define the mechanism (error, fatal or assertion) or which tool performs the check. The designer must decide.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-07T18:05:59+00:00): Out of scope of the simulation flow: the elaboration check of illegal parameters (REQ-PARAM-001, TEST-014) is a static job, one Verilator elaboration per illegal value with an elaboration-time $fatal in the verification source set. Mark these rules static_or_structural; do not check them in simulation.
3. ASM-001 is still Open and says a transfer that starts with PENABLE=1 is never answered. Is that hang an accepted behavior to test, or must the bridge recover or flag an error? (BR-20-01, BR-20-13) — *The spec says a transfer starting with PENABLE=1 is never answered, but ASM-001 and OI-002 are Open. It does not decide whether that hang is accepted behavior to test or whether the bridge must recover or flag an error. The designer must decide.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-07T18:05:59+00:00): Accepted limitation, not a DUT obligation: a transfer that starts with PENABLE=1 breaks REF-001 (APB4 Setup phase first), so ASM-001 stands. The testbench requester never produces it; the bridge need not answer, recover or flag it. Only the reset recovery (REQ-RESET-002) is verified. CHK-style tests must not expect a response to such a transfer.
4. What is the 'project-specific default value' for user signals generated by baseline sources? It must be defined before checking. (TL-T3.3-03) — *The TL-UL document does not define the project-specific default value for user signals; it is left to the project, and the layout is still TBD-001. The designer must define it. The bridge itself drives a_user to zero.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-07T18:05:59+00:00): For this DUT the project-specific default of the generated user bits is all zeros: o_tlul_a_user = '0 on every request (REQ-IF-005, DEC-004); the received d_user is ignored (DEC-006). Check a_user == 0 whenever a_valid is high.
5. Is the one-request-per-cycle limit a restatement of single-beat A-channel transfers, and is it on valid or on handshake? (TL-T3.2-03, TL-T3.2-04) — *The TL-UL text says only 'Only one request per cycle'. It does not say whether this restates single-beat transfers or whether it counts valid or the valid/ready handshake. The designer must clarify.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-07T18:05:59+00:00): It is a property of the handshake: at most one A-channel request accepted (a_valid and a_ready) and at most one D-channel response accepted (d_valid and d_ready) per cycle, which a single-channel TL-UL port satisfies by construction. For this bridge the stronger REQ-FUNC-004 applies: at most one request outstanding. No separate check beyond REQ-FUNC-004.

## Questions answered by the documents

- Does a misaligned access with PSTRB=4'b1111 or a read with arbitrary PSTRB also give PSLVERR=1? Is PSTRB ignored for reads? → Yes. A misaligned access gets PSLVERR=1 and no TL-UL request, even with PSTRB=4'b1111. A read ignores PSTRB, so any PSTRB value on a read is accepted. [T1:s6, 3:s3, 3:s17, 6.3:s15, 6.3:s16]
- When an error is returned, how many wait states does the PSLVERR response take, and is it timed relative to PSEL/PENABLE? → A local error (bad PSTRB or misaligned address) takes 0 wait states. PREADY and PSLVERR come together in the first Access cycle, and PSLVERR is asserted only with PREADY. A TL-UL error response has the same latency as a normal transfer (3 Access cycles with a prompt device). [3:s16, 3:s17, 3:s27, 3:s12, 6.3:s5, 10.2:s12]
- Does 'early launch' mean TL-UL a_valid is asserted in the very first APB access cycle (PENABLE=1) or in the setup cycle registered so it is visible at access? Exact cycle must be defined. → The request is captured at the edge that ends the Setup cycle, straight into the channel A flops. o_tlul_a_valid is therefore a flop output that is high in the first Access cycle (A1, PENABLE=1), one cycle after Setup. [3:s1, 5.3:s3, 5.3:s4, 5.3:s8, 21:s9]
- What is the exact error response behaviour (PSLVERR timing, whether a TL-UL request is suppressed) for unsupported PSTRB or misaligned address, given partial writes are excluded? → No TL-UL request is issued. The transfer completes with PREADY=1 and PSLVERR=1 in the first Access cycle, 1 Access cycle in total, with PRDATA=0. [3:s16, 3:s17, 10.2:s11, 3:s27, 12:s1]
- If a write has both PSTRB other than 4'b1111 and a misaligned PADDR, or if a read has PSTRB nonzero, how should the bridge respond? Does a rejected transfer issue any TL-UL request, and does PSLVERR use the same timing as a normal response? → Any illegal condition makes w_legal false, so there is a local error with no TL-UL request, and the response is the same whether one or both conditions apply. No priority between errors is needed. PSLVERR has the same first-Access-cycle timing. A read with nonzero PSTRB is legal because PSTRB is ignored on reads. [10.2:s3, 10.2:s5, 12:s7, 3:s3, 3:s16, 3:s17]
- What does 'misaligned' mean exactly (PADDR[1:0] != 0 for 32-bit words?), and does the check apply to reads and writes alike? → Misaligned means PADDR[1:0] is not 2'b00. The check applies to reads and writes alike. [3:s17, 10.2:s3, 9:s4]
- REQ-FUNC-001/REQ-FUNC-003 and REQ-IF-005: a_size is given as 2 and 2'b10, consistent. But REQ-IF-005 says a_param 3'b000 and a_user all zero while REQ-IF-002 says d_user unused. Confirm a_user width. → The a_user width is the parameter PARA_A_USER_W (default 1, range 1 to 32), and the bits are always driven to zero. The layout depends on the integration project (TBD-001), but the bridge drives zero either way. d_user is a separate, unused input. [8:s6, 6.2:s27, 20:s22, 3:s13, 6.2:s37]

Confirm that a_ready may be sampled in the first cycle. → Yes. a_valid is high in A1 and the request is accepted at the end of A1 when a_ready=1. A response in that same cycle is allowed and supported, which gives a 2-cycle Access phase. [5.3:s8, 5.3:s9, 5.3:s15, 6.3:s12, 3:s26]
- REQ-PERF-004 gives 4, 3 and 2 cycle Setup-to-Setup intervals. Which cycle counts as the start and end of each interval, and what exactly counts as a prompt device versus a same-cycle response? → The interval runs from one Setup cycle to the next. 4 cycles is S plus 3 Access cycles, 3 cycles is S plus 2 for a same-cycle response, and 2 cycles is S plus 1 for a local error. A prompt device accepts in A1 and responds in A2. A same-cycle response comes in the cycle in which the request is accepted. These are minimum intervals. [3:s28, 10.4:s3, 13:s1, 3:s25, 3:s26]
- Section 8 is referenced for illegal PARA_ADDR_W values. What does the design do if one is configured (elaboration error, undefined behaviour, or silent clamp)? A late response or a_ready held low extends the Access phase by the same number of cycles. o_apb_pready stays low until the response is loaded and the APB FSM reaches DONE. o_tlul_d_ready stays constant 1. [5.3:s16, 10.3:s23, 10.1:s6, 10.1:s7, 6.2:s29, 3:s14]

BR-6.2-04 says PRDATA holds its last value, and only the TL-UL error cases state PRDATA=0. → PRDATA is 0 for every error completion, including local errors.
