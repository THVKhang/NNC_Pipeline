## Open questions (the designer decides: `nnc answer <design> <n> "<decision>" --by <name>`)

1. REQ-FUNC-006 derives the Gray register from the next binary pointer, while REQ-FUNC-018 says flags are combinational from local pointer registers. Do the flags use the registered or the next pointer, and what is the exact full and empty equation, including the MSB inversion? (AF-3-07, AF-3-28, AF-3-10, AF-3-12) — *The spec says the flags are combinational from the local pointer registers and the synchronized pointer of the other domain, and the Gray register is derived from the next binary pointer. The exact full and empty equations (the MSB-inverted Gray compare or the binary compare) are not written anywhere. The designer must define them.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:04+00:00): Checked as behavior, not as one equation. Flags are combinational from the local pointer REGISTERS and the synchronized pointer of the other domain (REQ-FUNC-018, DEC-016). o_empty = 1 exactly when the read-domain occupancy estimate (synchronized write pointer minus read pointer register, modulo 2 x depth, the extra MSB distinguishing full from empty, glossary 'Binary pointer') is 0; o_full = 1 exactly when the write-domain estimate (write pointer register minus synchronized read pointer, modulo 2 x depth) equals PARA_AFIFO_DEPTH. Any Gray or binary implementation giving these values is compliant. 'Gray register derived from the next binary pointer' (REQ-FUNC-006) only means the Gray register is updated at the same edge as the binary register.
2. The thresholds must not change while the FIFO is in use. What counts as 'in use' (after reset release?), and is any behaviour defined if they change? (AF-3-17) — *The spec says the thresholds are written once before the FIFO is used and do not change while it is in use. It does not define 'in use' (for example after reset release or first access). It also does not define behavior if they change, and no check is specified. The designer must decide.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:04+00:00): 'In use' = from the release of both hardware resets to the end of the test. The thresholds are set before the resets are released and are not changed while in use (CDC-004, DEC-017). Changing them in use is outside the specification: no stimulus does it and no check covers it.
3. What are the full and empty values during software reset, and is the never-both-1 invariant exempt then? (AF-5.4-02, AF-5.3-07) — *The spec gives the values: o_full = 1 and o_empty = 1 while blocked. It also states INV-002 (full and empty never both 1) without an exemption. Both flags are 1 during the software reset, so the spec is inconsistent here. The designer must decide whether INV-002 and SVA-001 are exempt during software reset.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:04+00:00): The specific software-reset requirements prevail over INV-002: o_full = 1 while the write side is blocked (REQ-SRST-017, DEC-027) and o_empty = 1 while the read side is blocked (REQ-SRST-004). INV-002/SVA-001 (never both 1) is checked only outside a software-reset sequence, i.e. while i_rst_n_sw = 1 and o_sw_rst_busy = 0.
4. Are writes and reads blocked during software reset treated as rejected (INV-005) and does INV-004 apply then? (AF-5.4-04, AF-5.4-05, AF-5.3-07) — *Blocked accesses are not accepted and raise no overflow or underflow pulse. INV-005 and INV-004 are not stated to apply to the software-reset case. The reset itself resets the pointers and discards words, and the spec does not say whether the invariants are suspended. The designer must decide.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): A write or read blocked by the software reset is not a 'rejected' access of INV-005: it is not accepted, raises no pulse (DEC-028) and does not write the storage. The pointers are reset by the handshake itself. INV-004 and INV-005 apply to normal operation; during the sequence REQ-SRST-003/008/017 apply.
5. The CDC-004 thresholds are described as static and written before use. What is the exact meaning of 'before the FIFO is used', and is there a defined way to know when the FIFO is in use? Should the testbench check this? (AF-7.2-04) — *The spec only says the thresholds are static, written once before use, and not changed while the FIFO is in use. It does not define an observable event or signal for 'in use', and it specifies no testbench check. The designer must define it.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): Same decision as question 2: in use = after both hardware resets are released; thresholds are static from before that point; no check of a threshold change in use.
6. Illegal configurations list 'stage count outside 2..4', but CELL_TYPE allows 0 (S=0) and no stage-count parameter is defined. What does stage count refer to? (AF-8-14, AF-8-06) — *Section 8 lists 'stage count outside 2..4' as illegal, but no stage-count parameter exists (removed by DEC-039). Stages are set by PARA_AFIFO_CELL_TYPE, which also allows 0 stages. The spec does not reconcile this, so the designer must clarify what the stage-count illegality means.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): 'Stage count' means the synchronizer stages S set by PARA_AFIFO_CELL_TYPE (options 1..4 give S = 2, 2, 3, 4; section 14.4). Option 0 (S = 0, bypass) is not a legal option for the pointer crossings of this IP (section 14.4, 'Legal use') and is not verified; options above 4 are illegal (DEC-002). The IP does not check the value.
7. What exactly is 'after the reset has started' in step (3)? Is it detected by o_sw_rst_busy = 1 or by some number of cycles? (AF-11.2-03) — *Step (3) says to drive i_rst_n_sw back to 1 'after the reset has started' but does not define how to detect this (o_sw_rst_busy = 1 or a number of cycles). The spec shows that a one-cycle pulse is latched at the first write edge, but it does not name the criterion for software. The designer must define it.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): Software may release i_rst_n_sw after at least one write-clock edge has sampled it low: a one-cycle low pulse is legal (port table: 'It may be a one-cycle low pulse or a longer low level', DEC-026). Tests use both a one-cycle pulse and holding it low until o_sw_rst_busy = 1.
8. Does a software reset block (ERR-005) also suppress o_overflow/o_underflow pulses already pending from a request just before the reset begins? (AF-12-09, AF-12-03, AF-12-06) — *The spec says an access blocked by the software reset raises no pulse. It does not say whether an overflow or underflow pulse already due from a rejected request just before the block begins is suppressed or still shown. The designer must decide.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): Literal reading of DEC-028: only an access sampled at an edge where its side is blocked raises no pulse. A request rejected because full (empty) at an edge where the side was not yet blocked raises its normal one-cycle pulse in the next cycle (OP-003), even if the block starts in that cycle.
9. SVA-014 'bounded number of cycles' has no stated bound; what is it? (AF-15.3-15) — *SVA-014 requires both FSMs to return to RUN within a 'bounded number of cycles', but no numeric bound is given. The designer must define it.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-10T04:01:05+00:00): Bound for SVA-014 / REQ-SRST-013: with i_rst_n_sw = 1 and both clocks running, both FSMs are back in RUN within 8 x (S + 2) edges of the slower clock after the sequence starts (four crossings of the four-phase handshake, each at most S + 2 destination edges with the metastability model of REQ-VER-001, plus FSM steps; a factor 2 margin). For the default S = 2: 32 edges of the slower clock.

- AF-17.1.3-08 is garbled ('WHEN If'); which condition triggers the separate coverage requirement, and who is responsible? → The condition is that the project policy uses set_clock_groups. In that case the bounded-delay constraints and the CDC analysis shall cover the crossings separately. The IP owns the crossing constraints. [17.1.3:s8, 17.1.3:s7, 17.1:s1]
- Do the overflow and underflow flags clear only on reset, or can user logic clear them? What does 'recovery by user logic' mean at the interface level? → The flags are not sticky. They self-clear after one cycle, and the hardware reset also clears them. There is no clear input or register. 'Recovery by user logic' means the producer or consumer reacts to the flags, with no retry or drain provided. [12:s1, 12:s2, 12:s9, 11:s3, 18:s7]
- What is the technology cell option, and how is it selected (parameter or macro)? Can it be checked in simulation? → The technology cell option is the parameter PARA_AFIFO_CELL_TYPE (0 to 4), which selects the cell by wrapper parameter. The macro VLSIT_SYNTHESIS only selects the synthesis or simulation branch of the wrapper. It is checked in simulation for each option, in both branches. [8:s6, 3:s16, 14.4:s29, 15.2:s9]
- DEC-037 calls option 0 illegal for the pointer crossings and says a value above 4 gives the 4-FF cell. DEC-002 says there is no elaboration check and illegal values are undefined. Is a value above 4 defined or undefined? Is option 0 on a pointer crossing legal and tested? → A value above 4 is illegal and its behavior is undefined (not checked), even though the wrapper happens to give the 4-FF cell. Option 0 on the pointer crossings is not a legal use of the IP and is not checked. It is tested only at wrapper level. [14.4:s15, 14.4:s22, 14.4:s23, 20.2:s37, 20.2:s2, 14.4:s30]
- The default is 2 synchronizer stages (DEC-004), and the cell type also defaults to 2. How do the synchronizer-stage parameter and PARA_AFIFO_CELL_TYPE relate? Does the metastability latency S-1..S+1 depend on S or on the cell type? → There is no separate stage parameter. DEC-039 removed PARA_AFIFO_SYNC_STAGE, and S is set by PARA_AFIFO_CELL_TYPE (default 2, giving 2 stages). The metastability latency therefore depends on S through the cell type. [20.2:s39, 14.4:s19, 14.4:s18, 3:s54, 8:s6]
- Can occupancy for o_full_thr and o_empty_thr be checked exactly, given that each flag uses a synchronized, delayed pointer from the other domain? What tolerance applies? → The estimate is not exact at a given instant. It is pessimistic: the full side can read larger than the true occupancy and the empty side smaller. It differs from the true occupancy only by pointer updates still inside the synchronizer, which means S to S+2 edges with the model. No numeric tolerance is given beyond that. [3:s12, 9:s5, 10.3:s7, 10.3:s8]
- ASM-003 says read data stays stable under the pointer protocol, while DEC-012 randomizes the synchronizer latency per bit. Is any assertion on read-data stability expected? → Read-data correctness is checked by SVA-004 (scoreboard: a read returns the word written to that entry) and by a no-X check on accepted reads. The pointer protocol keeps the data stable regardless of the per-bit latency, with EXC-003 bounding the path. No separate stability assertion is listed. [15.3:s6, 10.6.3:s22, 20.1:s3, 10.4:s4, 15.3:s26]
- DEC-040 says the cell pins follow the naming rule (i_clk_dst, i_rst_n_dst/i_set_n_dst, i_d, o_q), but AF-20.2-37 says pins CK, RN/SN, D, Q and exempt from naming. Which is correct? → DEC-042 replaces DEC-040. The example cells keep the library pin names CK, RN or SN, D, Q and are exempt from the naming rule. [20.2:s42, 3:s56, 14.4:s8]
- DEC-041 says a same-edge read returns the old word in the macro model, but the wrapper simulation branch returns X. Which behaviour must the testbench check? → The macro model returns the old word on a same-edge read and write. The wrapper's simulation branch that returned X was removed by DEC-043, so the testbench checks the old-word behavior. [20.2:s43, 6.2:s87, 10.5:s4, 3:s55]
- Which flags are pessimistic (full, empty, almost-full, almost-empty)? How many cycles late may they deassert? → The full and empty flags are pessimistic, meaning they can be late to deassert but never early. The threshold flags are also derived from the synchronized pointer and are pessimistic. The lateness is up to S destination edges nominally and up to S+2 with the metastability model. No almost-full or almost-empty flags exist beyond the threshold flags. [3:s10, 3:s11, 3:s12, 10.3:s7, 21:s11]
