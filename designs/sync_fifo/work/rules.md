## Open questions (the designer decides: `nnc answer <design> <n> "<decision>" --by <name>`)

1. What counts as 'the writer/reader is not the limit' in the no-gap rule, and how is it measured in a scenario check? (SF-3-51) — *No operational definition of 'not the limit' or of a gap-count method is given. The text only says the side at the higher frequency is held back by the rate difference, and that the sweep measured the side that is not rate-limited. A checkable rule for a scenario check is missing.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-08T05:14:13+00:00): Operational definition for the run configuration: with i_wr_en and i_rd_en held at 1 and depth >= 4 + 2*PARA_SFIFO_PTR_RETIME, after the first word is visible (o_empty=0) every read-clock edge with i_rd_en=1 accepts a read (o_empty=0) and every write-clock edge with i_wr_en=1 accepts a write (o_full=0). With equal clock periods neither side is the limit, so both are checked; with unequal periods only the slower side is checked. Other clock ratios are other runs.
2. When a request arrives in REL, or a second pulse arrives, is it queued as one new sequence or one per pulse? Does a hardware reset clear a pending request? (SF-3-47, SF-3-46) — *The documents say a request arriving in REL, or a second pulse, is served as a new sequence once the write FSM is back in RUN. They do not say whether several pulses merge into one sequence or each gets its own, or whether a short pulse is remembered. A hardware reset does bring both FSMs to RUN and clears the request and acknowledge flops.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-08T05:14:14+00:00): A hardware reset clears a pending request (stated: it clears all FSMs, the request and the acknowledge). i_rst_n_sw is a level: a low level present when the write FSM is back in RUN starts one new complete sequence. Whether a pulse that starts and ends inside REL, or several pulses before RUN, are remembered or merged is not specified: tests must not rely on it and drive only requests that are still low when o_sw_rst_busy falls.
3. CFG-BASE says it is verified by all tests, but some tests (e.g. those requiring FEAT-007 or FEAT-010) may not apply to it; confirm. (SF-4-01) — *CFG-BASE lists 'All tests' as its verification target. Each test in 15.2 has its own configuration column: TEST-012 is CFG-MACRO only, and TEST-013 is CFG-MIN and CFG-ODD. The designer must say whether CFG-BASE's 'All tests' means only the tests that list CFG-BASE.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-08T05:14:14+00:00): Only the tests whose configuration column lists CFG-BASE apply to the default run. One simulation is one configuration; tests of CFG-RETIME, CFG-MACRO, CFG-ODD and CFG-MIN are other runs and are not verified by this run.
4. Pointers and occupancy are internal signals. Should assertions bind to internal RTL signals, or be derived from interface observables? (SF-9-01, SF-9-02, SF-9-03, SF-9-04) — *The documents list the assertions' intent but do not say whether they shall bind to internal RTL signals (pointers, occupancy, FSM state) or only to interface observables.    - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-08T05:14:14+00:00): Black-box: checks use only the top-level ports. Pointer, occupancy and FSM invariants are checked through their observable effects (flags, data order, busy) with a reference occupancy model built from accepted writes and reads; no internal signal is bound.
5. Is the new i_rst_n_sw low level during REL queued, and is a pulse shorter than the FSM time ever lost? The wording 'served after RUN' needs a precise latency. (SF-10.7-10, SF-10.7-08) — *The text says a new low level during REL is served after the write FSM is back in RUN. It does not give the latency or say whether a pulse that ends before RUN is remembered. The designer must define it.*
   - **Decision** (Claude (delegated by GabrielHCMUT), 2026-11-08T05:14:14+00:00): Same as decision 2: the latency is not specified, so tests use a bounded wait (no exact cycle count) and check that the new sequence completes (o_sw_rst_busy returns to 0, FIFO empty); a pulse that ends before RUN is not tested.

(SF-17.1.2-01) — *No number or threshold is given for a 'very small' launch-to-capture interval.
