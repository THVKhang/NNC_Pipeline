# Requirements (approved rules, gate G1)

Each rule cites the specification. Tag the RTL that implements a rule with `// REQ: <id>`.

- **SF-1.1-01** [MUST] (SyncFIFO_Design_Specification.md 1.1) The FIFO must transfer a stream of data words from the write clock domain to the read clock domain.
  - quote: "The IP transfers a stream of data words from a write clock domain to a read clock domain."
- **SF-1.1-02** [MUST] (SyncFIFO_Design_Specification.md 1.1) Words must be read in the same order in which they were written (first-in first-out).
  - quote: "Words are read in the order in which they were written."
- **SF-1.1-03** [MAY] (SyncFIFO_Design_Specification.md 1.1) The write and read clocks may have different frequencies, provided they are synchronous with a fixed phase relationship from one source.
  - quote: "The two clocks may have different frequencies, but they are synchronous to each other: both derive from one source and keep a fixed phase relationship, for example 150 MHz and 100 MHz taken from one PLL (DEC-005)."
- **SF-1.1-04** [MUST] (SyncFIFO_Design_Specification.md 1.1) Pointers must cross between clock domains without synchronizers, as ordinary timed paths closed by STA. Condition: clocks are synchronous.
  - quote: "Because the clocks are synchronous, the pointers cross from one domain to the other without synchronizers, as ordinary timed paths that static timing analysis (STA) closes."
- **SF-1.1-05** [MAY] (SyncFIFO_Design_Specification.md 1.1) The write and read clocks may be equal (single clock) as a normal use case.
  - quote: "The special case of two equal clocks (one clock) is a normal use."
- **SF-1.1-06** [MUST] (SyncFIFO_Design_Specification.md 1.1) The FIFO must provide write and read requests, full and empty flags, threshold flags, overflow and underflow pulses, show-ahead read, a hardware reset per domain and a software reset with handshake.
  - quote: "The interface and the options are inherited from the sibling IP 001_AsyncGrayFIFO (DEC-002), without its clock-domain-crossing logic: write and read requests with full and empty flags, threshold flags, overflow and underflow pulses, a show-ahead read, a hardware reset per domain, and a software reset with a handshake."

## Decisions on questions the specification left open

- Rules SF-3-51: What counts as 'the writer/reader is not the limit' in the no-gap rule, and how is it measured in a scenario check?
  - **Decision:** Operational definition for the run configuration: with i_wr_en and i_rd_en held at 1 and depth >= 4 + 2*PARA_SFIFO_PTR_RETIME, after the first word is visible (o_empty=0) every read-clock edge with i_rd_en=1 accepts a read (o_empty=0) and every write-clock edge with i_wr_en=1 accepts a write (o_full=0). With equal clock periods neither side is the limit, so both are checked; with unequal periods only the slower side is checked. Other clock ratios are other runs.
- Rules SF-3-47, SF-3-46: When a request arrives in REL, or a second pulse arrives, is it queued as one new sequence or one per pulse? Does a hardware reset clear a pending request?
  - **Decision:** A hardware reset clears a pending request (stated: it clears all FSMs, the request and the acknowledge). i_rst_n_sw is a level: a low level present when the write FSM is back in RUN starts one new complete sequence. Whether a pulse that starts and ends inside REL, or several pulses before RUN, are remembered or merged is not specified: tests must not rely on it and drive only requests that are still low when o_sw_rst_busy falls.
- Rules SF-4-01: CFG-BASE says it is verified by all tests, but some tests (e.g. those requiring FEAT-007 or FEAT-010) may not apply to it; confirm.
  - **Decision:** Only the tests whose configuration column lists CFG-BASE apply to the default run. One simulation is one configuration; tests of CFG-RETIME, CFG-MACRO, CFG-ODD and CFG-MIN are other runs and are not verified by this run.
- Rules SF-9-01, SF-9-02, SF-9-03, SF-9-04: Pointers and occupancy are internal signals. Should assertions bind to internal RTL signals, or be derived from interface observables?
  - **Decision:** Black-box: checks use only the top-level ports. Pointer, occupancy and FSM invariants are checked through their observable effects (flags, data order, busy) with a reference occupancy model built from accepted writes and reads; no internal signal is bound.
- Rules SF-10.7-10, SF-10.7-08: Is the new i_rst_n_sw low level during REL queued, and is a pulse shorter than the FSM time ever lost? The wording 'served after RUN' needs a precise latency.
  - **Decision:** Same as decision 2: the latency is not specified, so tests use a bounded wait (no exact cycle count) and check that the new sequence completes (o_sw_rst_busy returns to 0, FIFO empty); a pulse that ends before RUN is not tested.
- Rules SF-17.1.2-01: Which clock ratios count as making the launch-to-capture interval 'very small'? Please give a number or threshold for SF-17.1.2-01.
  - **Decision:** Static timing (STA) item, not observable in simulation: not verifiable by simulation.
- Rules SF-20.2-04, SF-20.2-05: DEC-021 is the author's choice and is still to be confirmed by the designer. Should the strict own-domain-flag acceptance with no full-FIFO bypass be treated as final before checks are built?
  - **Decision:** Verify the requirement text as written (DEC-021): a write is accepted only when i_wr_en=1 and o_full=0, a read only when i_rd_en=1 and o_empty=0, with no full-FIFO bypass. The designer's confirmation of DEC-021 stays an open item of the specification and is reported.
- Rules SF-1.1-13, SF-1.3-02, SF-1.3-03: The quote does not define the exact latency or the exact static threshold values and how full/empty flags are timed across the two domains. Settle these before verification.
  - **Answer from the text:** They are defined. Flag latency is the first (PTR_RETIME=0) or second (PTR_RETIME=1) strictly later destination edge. The thresholds are static inputs, compared with the occupancy seen by each side (o_full_thr: occupancy >= i_full_thr; o_empty_thr: occupancy <= i_empty_thr).
- Rules SF-1.1-06, SF-1.1-14: SF-1.1-06 lists a software reset with handshake while SF-1.1-14 requires a four-phase handshake. Should the reset behavior and its REQ-SRST requirements be specified in detail?
  - **Answer from the text:** Yes. The reset behavior is specified in detail in REQ-SRST-001..008 and Section 10.7, including the four-phase handshake.
- Rules SF-1.1-03, SF-1.3-01: The clocks are required to be synchronous with a fixed phase relationship, but no behavior is specified if they are not. Is that in or out of scope?
  - **Answer from the text:** Out of scope. Asynchronous clocks are excluded (use 001_AsyncGrayFIFO). Behavior is not specified for unrelated clocks, and wrong clock declarations would break the IP.
- Rules SF-3-10, SF-3-22, SF-3-30: Is o_rd_data required valid whenever o_empty=0 even with PTR_RETIME=1, and is it unreset? REQ-IF-003 says not reset while REQ-RESET-001 resets every flop; clarify o_rd_data exclusion.
  - **Answer from the text:** o_rd_data is valid whenever o_empty=0 in all configurations, including PTR_RETIME=1. It is not reset because it is the memory output register. The memory is the only resetless storage, so REQ-RESET-001's 'every flip-flop' does not cover it.
- Rules SF-3-21, SF-3-01, SF-3-02: What exactly are the one-gate combination and the reset block term for the flags under software reset, and are flags forced during software reset? The reset values listed omit this.
  - **Answer from the text:** Write block = o_sw_rst_busy flop OR i_rst_n_sw=0. Read block = request seen on the read side OR read FSM not in RUN. o_full = block OR full flop; o_empty = block OR empty flop. o_full_thr = (i_full_thr==0) when blocked, else its flop. o_empty_thr = 1 when blocked, else its flop. So the flags are forced during software reset.
- Rules SF-3-06, SF-3-09, SF-3-28: What is the exact latency of flags with PARA_SFIFO_PTR_RETIME 0 versus 1? 'Conservative' flags are not bounded, so no checkable bound exists.
  - **Answer from the text:** With PTR_RETIME=0, o_empty falls after the first read edge strictly after the write edge, and o_full falls after the first write edge strictly after the read edge. With PTR_RETIME=1 it is the second such edge. Boundary flags are exact in their own domain. The bound is therefore a number of destination edges.
- Rules SF-3-14, SF-3-15: Does occupancy for thresholds use the conservative visible occupancy including pointer retiming?
  - **Answer from the text:** Yes. The threshold flags use the occupancy computed from the other side's pointer view, which is the direct pointer or the retiming flop, and which may lag.
- Rules SF-3-33, SF-3-34, SF-3-48: The 'hold state' and the 'hold' phase of the sequence are not defined in these quotes. Which FSM state is meant, and how many cycles does the low level have to be held before the sequence reaches it?
  - **Answer from the text:** The hold state is the write FSM state ENUM_ST_HOLD, entered after PTR (once the acknowledge is seen), where it waits for i_rst_n_sw=1. A one-cycle low is enough to start the sequence. The low level only has to be held if the user wants to stay in HOLD. The exact number of cycles to reach HOLD is not fixed (a few cycles of both clocks, depending on handshake and ratio).
- Rules SF-3-35, SF-3-36, SF-3-44: Is the o_sw_rst_busy window (1 from the cycle after the write FSM takes the request) consistent with writes being blocked from the cycle where i_rst_n_sw=0? Which signal marks the first blocked cycle in the cycle between the request and busy rising?
  - **Answer from the text:** Consistent. The write block term is busy OR i_rst_n_sw=0, so the first blocked cycle is the one in which i_rst_n_sw=0 (no flop). Busy rises one cycle after the FSM takes the request and continues the block.
- Rules SF-4-02, SF-4-03: CFG-RETIME says 'CFG-BASE plus FEAT-007' but lists FEAT-010 as disabled, while CFG-BASE already has FEAT-010 disabled; confirm CFG-RETIME/CFG-MACRO inherit CFG-BASE's DATA_W 32 and DEPTH 8.
  - **Answer from the text:** Yes. CFG-RETIME and CFG-MACRO are defined as CFG-BASE plus one feature, so they keep DATA_W 32 and DEPTH 8 (the defaults) unless overridden. The repeated 'FEAT-010 disabled' is redundant but consistent.
- Rules SF-4-04, SF-4-05, SF-4-08: CFG-ODD and CFG-MIN do not state whether DEPTH 5/12 are the only tested values, and whether DEPTH 2 with DATA_W 1 are legal given Section 8's illegal combinations (not provided).
  - **Answer from the text:** DEPTH 5 and 12 are examples ('for example'), not the only values. TEST-008 uses 2, 3, 5, 7, 12, 16. DEPTH 2 with DATA_W 1 is the smallest legal instance. The illegal values are a depth below 2, a width of 0, and an option outside 0..1.
- Rules SF-5.4-03, SF-5.1-01, SF-5.4-04: SF-5.4-03 says o_full is 1 whenever occupancy is DEPTH and o_empty is 1 whenever occupancy is 0, but flags are conservative due to cross-domain lag. Is the full/empty guarantee measured with real or visible pointers, and may full/empty also be asserted at occupancy below depth/above zero?
  - **Answer from the text:** The guarantee is against the real stored count: o_full is 1 whenever DEPTH words are stored, and o_empty is 1 whenever occupancy is 0. Because the views only lag, o_full may also be 1 with a place free (the freed place is not yet visible), and o_empty may be 1 while a word exists but is not yet visible. The views never err in the unsafe direction.
- Rules SF-5.3-02, SF-5.3-05: SF-5.3-02 and 5.3-05 depend on whether the retiming flops are present (optional). Which parameter selects them, and should visibility latency checks cover both configurations?
  - **Answer from the text:** The parameter PARA_SFIFO_PTR_RETIME (0 = direct, 1 = one retiming flop) selects the retiming flops. The latency checks shall cover both values (TEST-006 uses CFG-BASE and CFG-RETIME).
- Rules SF-6.3-06, SF-6.3-11: Is the overflow/underflow pulse raised when a write/read is rejected for full/empty only, and what is its exact timing relative to software-reset blocking?
  - **Answer from the text:** The pulse is raised only for a write or read requested while o_full or o_empty is 1 and the side is not blocked by software reset. It appears in the cycle after the rejected request. A request blocked by software reset gives no pulse.
- Rules SF-6.3-03, SF-6.2-07: Does o_rd_data validity depend on o_empty only, or also on software-reset read blocking?
  - **Answer from the text:** o_rd_data is valid whenever o_empty=0. During a software-reset read block o_empty is 1, so validity depends on o_empty alone and the blocking is included through it.
- Rules SF-7.2-01, SF-7.2-02: Is the quote for the clock constraint complete? It is truncated at 'related c', so the no-false-path and no-async-clock-group requirement cannot be confirmed.
  - **Answer from the text:** The full requirement is in the documents: the two clocks shall be declared as related clocks of one source, and no asynchronous clock group or false path shall be set between them.
- Rules SF-7.3-01, SF-7.3-02, SF-7.3-05: Is the write pointer reset to 0 and o_full reset to 0 consistent with the rule that all flip-flops reset to 0 except o_empty and o_empty_thr? Do the FSM RUN encoding and the retiming flops also reset to 0?
  - **Answer from the text:** Yes. All flops reset to 0 except o_empty and o_empty_thr, which reset to 1. The write pointer and o_full are 0. Reset scope includes the FSMs (RUN), request/acknowledge flops and retiming flops, all at 0. The memory output register is the only resetless element.
- Rules SF-8-03, SF-8-10, SF-8-14: Is the IP's behavior defined for depths that are not a power of 2, given the pointer spans 0 to 2xDEPTH-1? Also what is the minimum legal depth relative to gap-free streaming?
  - **Answer from the text:** Yes. Any depth of 2 or more is supported, with pointers counting modulo 2xDEPTH (0 to 2xDEPTH-1) and the address equal to the pointer modulo DEPTH. Depths below 4+2xPTR_RETIME are legal but do not guarantee gap-free streaming.
- Rules SF-8-09, SF-8-10, SF-8-11: LPARA_ADDR_W is at least 1 and LPARA_OCC_W/PTR_W at least 2; confirm these hold for DEPTH=2 with clog2 and whether the derived values can be overridden.
  - **Answer from the text:** The derived widths are clog2(DEPTH), clog2(2xDEPTH) and clog2(DEPTH+1). For DEPTH=2 they give 1, 2 and 2, which meet the stated minima. They are localparams derived from the depth, not parameters.
- Rules SF-9-05, SF-9-06: Is the threshold input (LPARA_OCC_W wide) allowed to hold values above DEPTH, and how are o_full_thr and o_empty_thr defined at threshold = DEPTH and 0? The range says 0 to DEPTH but an overflow case is described.
  - **Answer from the text:** The legal range is 0 to DEPTH. A value above DEPTH makes o_full_thr never 1 and o_empty_thr always 1. o_full_thr = occupancy >= i_full_thr and o_empty_thr = occupancy <= i_empty_thr, so a threshold of 0 or DEPTH follows those formulas. While blocked, o_full_thr = (i_full_thr==0).
- Rules SF-10.2-02, SF-10.3-13, SF-10.4-03, SF-10.4-04: The write-side latency to o_empty fall is described as 'first later read edge' in 10.2, but 10.4 gives 2 ns for PTR_RETIME 0 and 3 cycles for equal clocks. How are coinciding edges handled for non-equal ratios?
  - **Answer from the text:** A coincident edge does not count as 'strictly later', so the pointer is seen at the next edge. This applies to equal clocks and to coincident edges at the LCM of other ratios. The 2 ns figure is for 12/8 ns clocks (the first read edge is only 2 ns later). The 2 cycles apply to equal clocks.
- Rules SF-10.4-09: SF-10.4-09 gives a depth formula of 4+2×RETIME, but the sweep table shows lower depths for other ratios. Is the requirement the worst-case depth only?
  - **Answer from the text:** Yes. 4+2xPTR_RETIME is the guaranteed sufficient depth, equal to the measured worst case over the tested ratios. Other ratios may need less, but only this depth is guaranteed. It is a measured condition, not a proof.
- Rules SF-10.2-01, SF-10.3-09, SF-10.4-07: o_full is said to rise 'at once' in 10.2 but 'in the next cycle' in 10.3 and 10.4. Is this the same timing?
  - **Answer from the text:** Same timing. o_full is a look-ahead flop, so it is 1 in the cycle after the write that stores the last place, with no extra latency. 'At once' means no added latency.
- Rules SF-10.6-02, SF-10.6-05: With PARA_SFIFO_PTR_RETIME=1, do the flag formulas and the 'never under/over-estimates' guarantee change latency bounds? The exact cycle timing needs settling.
  - **Answer from the text:** With PTR_RETIME=1 the views use the retiming flop of the other pointer. That only adds one destination edge of latency, and the function is unchanged. The 'never underestimate' and 'never overestimate' guarantees hold because the views only lag.
- Rules SF-10.7-01, SF-10.6-03: Is o_full=1 from the same cycle as i_rst_n_sw=0 (combinational) consistent with 'o_full is a flop output' in the write-domain intro?
  - **Answer from the text:** Consistent. The full flag is a flop, and the o_full port is the flop ORed with the block term by one gate. This one gate is the stated exception, so the port follows i_rst_n_sw with no clock delay.
- Rules SF-12-01, SF-12-03, SF-12-04, SF-12-06: ERR-001/002 say the pulse lasts one cycle and 'cleared by reset'. Can a pulse be in progress when reset occurs, and is it cut short? Also, is the pulse in the cycle after the request or the same cycle?
  - **Answer from the text:** The pulse is raised in the cycle after the rejected request. A hardware reset asserts asynchronously and sets every flop of the domain to its reset value, with o_overflow and o_underflow at 0. A pulse in progress is therefore cut short.
- Rules SF-12-11, SF-12-01, SF-12-04: For consecutive rejected requests, is the o_overflow/o_underflow pulse held high continuously (merged) or does it appear as one pulse per request? 'Consecutive' is ambiguous.
  - **Answer from the text:** Consecutive rejected requests give consecutive pulses. The pulse flop is loaded from the request condition every cycle, so for rejected requests in consecutive cycles it is high in consecutive cycles.
- Rules SF-13-04, SF-13-03: PERF-004 does not say which PARA_SFIFO_PTR_RETIME value gives the first write edge and which gives the second. Is it the same mapping as PERF-003 (0 gives first, 1 gives second)?
  - **Answer from the text:** Yes, the same mapping: PTR_RETIME=0 gives the first strictly later write edge and PTR_RETIME=1 gives the second.
- Rules SF-13-02: PERF-002 does not define the initial latency. Is it a fixed number of cycles, or does it depend on PTR_RETIME? What counts as a gap: a cycle where the FIFO could transfer a word but does not?
  - **Answer from the text:** The initial latency is not a single fixed number. It depends on PTR_RETIME and on the clock ratio and alignment. For equal clocks the first read is accepted 2 cycles after the write with PTR_RETIME=0 and 3 cycles with PTR_RETIME=1. For other ratios it follows the first or second strictly later edge. A gap is a cycle where the side is not rate-limited and does not accept a request with its enable held at 1.
- Rules SF-13-01, SF-13-02: PERF-001 requires depth of 2 or more, but PERF-002 requires depth of at least 4 + 2 x PTR_RETIME. Is sustained throughput at depths 2 and 3 allowed to have gaps, and what is the exact difference between the two metrics?
  - **Answer from the text:** Yes. Throughput of one word per cycle per side (REQ-PERF-001) is for any depth of 2 or more. Gap-free streaming after the initial latency is guaranteed only at depth >= 4+2xPTR_RETIME. Smaller depths are legal and correct but may show a gap.
- Rules SF-14.2.1-10, SF-14.2.1-06: Is o_ack_rd (and the busy/REL FSM state) observable at the interface? The 'edge that leaves RST/ACK' references internal FSM states, so how should the check be written?
  - **Answer from the text:** No. o_ack_rd is an internal port between m_vlsit_sfifo_rd and m_vlsit_sfifo_wr and is not in the top port list. o_ack_rd is 1 from the edge that leaves RST until the edge that leaves ACK. At the top, only o_sw_rst_busy, o_empty and similar signals are observable. Internal checks such as SVA-010 refer to FSM state.
- Rules SF-14.2.1-01: The i_wr_ptr and i_req_wr retiming statement is cut off in the quote. Confirm that PARA_SFIFO_PTR_RETIME applies to all four cross-domain inputs.
  - **Answer from the text:** Yes. The retiming applies to all cross-domain inputs: i_rd_ptr, i_wr_ptr, i_ack_rd and i_req_wr. Each is used directly or captured by one flop when PARA_SFIFO_PTR_RETIME=1. The handshake signals follow the parameter like the pointers.
- Rules SF-15.1-02, SF-15.2-09: TEST-011 lists ratio 9:2, but Section 15.1 ratio list omits it. Which ratio set is required?
  - **Answer from the text:** TEST-011's list is the required set (equal, 3:2, 2:3, 1:2, 2:1, 3:7, 7:3, 9:2, with coincident edges). COV-003 requires all ratios of TEST-011 to be hit. The 15.1 list describes how the environment varies the ratio.
- Rules SF-15.2-08, SF-15.2-14: TEST-017 uses depths 2,3,5,8,12 while TEST-008 uses 2,3,5,7,12,16; is the difference intended?
  - **Answer from the text:** Each test follows its own requirement. TEST-017 uses the REQ-VER-002 depths 2, 3, 5, 8, 12 for the scoreboard regression. TEST-008 uses 2, 3, 5, 7, 12, 16 for REQ-FUNC-006 pointer-wrap coverage. The two sets are specified separately and are not contradictory.
- Rules SF-16-01, SF-16-02: Both quotes are headed 'Not required' (no detailed DFT specification) but also contain 'shall' constraints. Should the structural constraints (no latch, loop, tri-state, clock gating or derived clock, and no DFT ports) be enforced as binding requirements, for example through lint or port-list checks, or are they informational?
  - **Answer from the text:** Binding. 'Not required' applies to a detailed DFT specification. The statement that the RTL shall contain no latch, combinational loop, tri-state, clock gating or derived clock is a 'shall', which is mandatory and testable. The IP has no DFT ports. The document does not give a specific TEST for the structural constraints in Section 16.
- Rules SF-17.1.3-01, SF-17.1.3-02: SF-17.1.3-02 forbids any false path on the crossing paths, while EXC-001 allows a false path to the flag flops from the static threshold inputs. Please confirm that the threshold ports are not 'crossing paths', so the two rules don't contradict each other.
  - **Answer from the text:** No contradiction. Crossing paths are the pointer, request and acknowledge paths between CLK-WR and CLK-RD. EXC-001 covers only the static, clockless threshold ports to the flag flops, and the false-path ban is on paths between the two clocks.
