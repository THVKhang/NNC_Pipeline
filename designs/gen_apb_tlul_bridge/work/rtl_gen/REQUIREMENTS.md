Feature ID: FEAT-003; Feature: Early launch of the TL-UL request from flip-flops; Required / optional: Required; Configuration condition: Always present; Requirements: REQ-FUNC-001, REQ-PERF-001"

## Decisions on questions the specification left open

- Rules BR-5.3-02, BR-5.4-02, BR-5.4-04, BR-5.3-11: Which internal signals can be observed by the testbench (FSM states, reg_a_valid)? Several rules refer to internal state.
  - **Decision:** Black-box only: tests and checkers observe the top-level ports and nothing inside the DUT (REQ-VER-001 binds the checkers to the ports). Rules about internal registers and FSM states (BR-5.3-02, BR-5.4-02, BR-5.4-04, BR-5.3-11) are verified through their port-visible effects: request on channel A in the first Access cycle, a_valid held and channel A stable until a_ready, PREADY one cycle, next Setup accepted in the cycle after PREADY. The internal state itself is not_observable_at_interface.
- Rules BR-8-09, BR-8-10: How should an illegal parameter be reported at elaboration of the verification source set (error, fatal, or assertion), and which tool performs the check?
  - **Decision:** Out of scope of the simulation flow: the elaboration check of illegal parameters (REQ-PARAM-001, TEST-014) is a static job, one Verilator elaboration per illegal value with an elaboration-time $fatal in the verification source set. Mark these rules static_or_structural; do not check them in simulation.
- Rules BR-20-01, BR-20-13: ASM-001 is still Open and says a transfer that starts with PENABLE=1 is never answered. Is that hang an accepted behavior to test, or must the bridge recover or flag an error?
  - **Decision:** Accepted limitation, not a DUT obligation: a transfer that starts with PENABLE=1 breaks REF-001 (APB4 Setup phase first), so ASM-001 stands. The testbench requester never produces it; the bridge need not answer, recover or flag it. Only the reset recovery (REQ-RESET-002) is verified. CHK-style tests must not expect a response to such a transfer.
- Rules TL-T3.3-03: What is the 'project-specific default value' for user signals generated by baseline sources? It must be defined before checking.
  - **Decision:** For this DUT the project-specific default of the generated user bits is all zeros: o_tlul_a_user = '0 on every request (REQ-IF-005, DEC-004); the received d_user is ignored (DEC-006). Check a_user == 0 whenever a_valid is high.
- Rules TL-T3.2-03, TL-T3.2-04: Is the one-request-per-cycle limit a restatement of single-beat A-channel transfers, and is it on valid or on handshake?
  - **Decision:** It is a property of the handshake: at most one A-channel request accepted (a_valid and a_ready) and at most one D-channel response accepted (d_valid and d_ready) per cycle, which a single-channel TL-UL port satisfies by construction. For this bridge the stronger REQ-FUNC-004 applies: at most one request outstanding. No separate check beyond REQ-FUNC-004.
- Rules BR-T1-03, BR-T1-04: Does a misaligned access with PSTRB=4'b1111 or a read with arbitrary PSTRB also give PSLVERR=1? Is PSTRB ignored for reads?
  - **Answer from the text:** Yes. A misaligned access gets PSLVERR=1 and no TL-UL request, even with PSTRB=4'b1111. A read ignores PSTRB, so any PSTRB value on a read is accepted.
- Rules BR-T1-04, BR-T1-05: When an error is returned, how many wait states does the PSLVERR response take, and is it timed relative to PSEL/PENABLE?
  - **Answer from the text:** A local error (bad PSTRB or misaligned address) takes 0 wait states. PREADY and PSLVERR come together in the first Access cycle, and PSLVERR is asserted only with PREADY. A TL-UL error response has the same latency as a normal transfer (3 Access cycles with a prompt device).
- Rules BR-1.1-02: Does 'early launch' mean TL-UL a_valid is asserted in the very first APB access cycle (PENABLE=1) or in the setup cycle registered so it is visible at access? Exact cycle must be defined.
  - **Answer from the text:** The request is captured at the edge that ends the Setup cycle, straight into the channel A flops. o_tlul_a_valid is therefore a flop output that is high in the first Access cycle (A1, PENABLE=1), one cycle after Setup.
- Rules BR-1.1-04, BR-1.3-03: What is the exact error response behaviour (PSLVERR timing, whether a TL-UL request is suppressed) for unsupported PSTRB or misaligned address, given partial writes are excluded?
  - **Answer from the text:** No TL-UL request is issued. The transfer completes with PREADY=1 and PSLVERR=1 in the first Access cycle, 1 Access cycle in total, with PRDATA=0.
- Rules BR-2.3-01, BR-2.3-02: If a write has both PSTRB other than 4'b1111 and a misaligned PADDR, or if a read has PSTRB nonzero, how should the bridge respond? Does a rejected transfer issue any TL-UL request, and does PSLVERR use the same timing as a normal response?
  - **Answer from the text:** Any illegal condition makes w_legal false, so there is a local error with no TL-UL request, and the response is the same whether one or both conditions apply. No priority between errors is needed. PSLVERR has the same first-Access-cycle timing. A read with nonzero PSTRB is legal because PSTRB is ignored on reads.
- Rules BR-2.3-02: What does 'misaligned' mean exactly (PADDR[1:0] != 0 for 32-bit words?), and does the check apply to reads and writes alike?
  - **Answer from the text:** Misaligned means PADDR[1:0] is not 2'b00. The check applies to reads and writes alike.
- Rules BR-3-20, BR-3-16: REQ-FUNC-001/REQ-FUNC-003 and REQ-IF-005: a_size is given as 2 and 2'b10, consistent. But REQ-IF-005 says a_param 3'b000 and a_user all zero while REQ-IF-002 says d_user unused. Confirm a_user width.
  - **Answer from the text:** The a_user width is the parameter PARA_A_USER_W (default 1, range 1 to 32), and the bits are always driven to zero. The layout depends on the integration project (TBD-001), but the bridge drives zero either way. d_user is a separate, unused input.
- Rules BR-3-34, BR-3-35: REQ-PERF-001 says 3-cycle Access (2 wait states) but REQ-PERF-002 says 2 cycles when the response arrives in the acceptance cycle. Confirm that a_ready may be sampled in the first cycle.
  - **Answer from the text:** Yes. a_valid is high in A1 and the request is accepted at the end of A1 when a_ready=1. A response in that same cycle is allowed and supported, which gives a 2-cycle Access phase.
- Rules BR-3-38: REQ-PERF-004 gives 4, 3 and 2 cycle Setup-to-Setup intervals. Which cycle counts as the start and end of each interval, and what exactly counts as a prompt device versus a same-cycle response?
  - **Answer from the text:** The interval runs from one Setup cycle to the next. 4 cycles is S plus 3 Access cycles, 3 cycles is S plus 2 for a same-cycle response, and 2 cycles is S plus 1 for a local error. A prompt device accepts in A1 and responds in A2. A same-cycle response comes in the cycle in which the request is accepted. These are minimum intervals.
- Rules BR-4-02: Section 8 is referenced for illegal PARA_ADDR_W values. What does the design do if one is configured (elaboration error, undefined behaviour, or silent clamp)? This decides whether illegal values can be tested at all.
  - **Answer from the text:** An illegal value is reported at elaboration of the verification source set and is never silently clamped.
- Rules BR-5.3-09, BR-5.3-06: Does 'the Access phase is extended' when the response is late mean o_apb_pready stays low and o_tlul_d_ready stays 1? A1/A2/A3 timing is not defined for a late response.
  - **Answer from the text:** Yes. A late response or a_ready held low extends the Access phase by the same number of cycles. o_apb_pready stays low until the response is loaded and the APB FSM reaches DONE. o_tlul_d_ready stays constant 1.
- Rules BR-6.2-01, BR-6.2-02, BR-6.3-11, BR-6.3-13: BR-6.2-01 and BR-6.2-02 say PADDR[1:0] must be 0 and PSTRB must be 4'b1111 on writes, but BR-6.3-11 and BR-6.3-13 define the bridge's PSLVERR behaviour for violations. Are these input constraints on the master, or only conditions the bridge handles? Should the assertions be disabled in the error-injection tests?
  - **Answer from the text:** They are conditions the bridge handles, not prohibitions on the master. The bridge rejects them with PSLVERR and no TL-UL request, and the APB Requester model deliberately drives illegal requests. The bit-must-be-0 notes mean the legal value for a successful transfer.
- Rules BR-6.2-04, BR-6.3-11, BR-6.3-13, BR-6.3-14: For locally detected errors (bad PSTRB or unaligned address), what value does PRDATA take when PREADY and PSLVERR are 1? BR-6.2-04 says PRDATA holds its last value, and only the TL-UL error cases state PRDATA=0.
  - **Answer from the text:** PRDATA is 0 for every error completion, including local errors. The 'holds its last value' text applies only when PREADY is not asserted.
- Rules BR-6.3-09, BR-6.2-06: For a TL-UL response in the same cycle as request acceptance, what is the exact timing of PREADY relative to the A-channel handshake? Does o_tlul_a_valid drop in that cycle? BR-6.2-06 holds the valid until a_ready.
  - **Answer from the text:** The response is loaded at the end of A1, so PREADY is 1 in A2 (2-cycle Access phase). o_tlul_a_valid is still high in A1, the acceptance cycle, and is cleared when the request is accepted, so it is low in A2.
- Rules BR-6.2-15, BR-6.3-08: o_tlul_d_ready is 0 in reset and 1 only after the first clock edge following reset release. How should a D response in that window be treated: discarded as an orphan or accepted?
  - **Answer from the text:** A response in that window is discarded as an orphan. The TL-UL FSM is IDLE, a response counts only in WAIT or in REQ with a_ready, and w_resp_hit also needs reg_d_ready. No request can be outstanding in the first cycle.
- Rules BR-7.3-02, BR-7.3-03: The Reset value row lists reg_a_rd, reg_a_addr and reg_a_data as reset to 0, and the rule says o_tlul_a_opcode = 3'b000. Is opcode derived from reg_a_rd, so that 000 (PutFullData) is the reset value? Please confirm the mapping.
  - **Answer from the text:** Yes. Opcode bit 2 comes from the reg_a_rd flop (1 = Get) and bits [1:0] are constant 0. reg_a_rd resets to 0, so the reset opcode is 3'b000.
- Rules BR-7.3-01: Synchronous release is provided by the SoC reset controller. Should verification check the release timing, or assume it as an environment constraint?
  - **Answer from the text:** Synchronous release is provided by the SoC reset controller. It is an integration dependency, not behavior of the bridge, so it is an environment assumption.
- Rules BR-8-05: The a_user layout depends on the integration project (TBD-001). Is the always-zero requirement final for all widths?
  - **Answer from the text:** Yes. a_user is always driven to zero (DEC-004). Only the width is a parameter, and the bridge drives zero whatever the layout in TBD-001.
- Rules BR-8-03, BR-8-04: Is PARA_SRC_ID range 0 to 2^PARA_SRC_W - 1 checked at elaboration, and what is the expected d_source behavior when a response carries a different source?
  - **Answer from the text:** PARA_SRC_ID must fit in PARA_SRC_W bits (range 0 to 2^PARA_SRC_W-1), and an illegal value is reported at elaboration. A response with d_source different from PARA_SRC_ID completes with PSLVERR=1 (and PRDATA=0).
- Rules BR-9-02, BR-9-04, BR-9-03: BR-9-02 and BR-9-04: Is a non-word-aligned address a master-side prohibition or a slave-side error response? Should the bridge still issue a TL-UL request when PADDR[1:0]!=0, or suppress it while returning PSLVERR?
  - **Answer from the text:** It is a slave-side error response. With PADDR[1:0] not 00 the bridge suppresses the TL-UL request and returns PSLVERR with PREADY.
- Rules BR-9-09, BR-9-10: BR-9-09: How is the expected d_opcode determined when the request was an error/suppressed one, and does a d_error from the TL-UL side also yield PSLVERR?
  - **Answer from the text:** A suppressed request has no TL-UL request and no response to check. For accepted requests the expected d_opcode is 001 for a read and 000 for a write. A TL-UL d_error=1 yields PSLVERR=1.
- Rules BR-9-01, BR-9-08: BR-9-08: PSTRB is mentioned in BR-9-01, but a_mask is always 4'b1111. How are partial PSTRB writes handled (DEC-001)? Is PSTRB != 4'hF an error or ignored?
  - **Answer from the text:** A write with PSTRB other than 4'b1111 is an error. It gets PSLVERR=1 in the first Access cycle with no TL-UL request. It is not ignored, and a_mask is always 4'b1111.
- Rules BR-10.1-02, BR-10.3-01: Does the first Access cycle for an illegal request mean PREADY is asserted in the cycle right after Setup (consistent with reg_pready set at the Setup edge)? Is the APB Access phase (penable=1) one cycle for the illegal case?
  - **Answer from the text:** Yes. The response flops are loaded at the end of Setup, so PREADY=1 and PSLVERR=1 in the cycle right after Setup. That is a 1-cycle Access phase (PENABLE=1).
- Rules BR-10.1-01, BR-10.3-03: For a legal request, does the TL-UL FSM go to REQ at the Setup edge simultaneously with the APB FSM going to BUSY, and how does this relate to launch via w_req_launch?
  - **Answer from the text:** Yes. At the Setup edge of a legal request, w_req_launch makes the TL-UL FSM go to REQ and load the channel A flops, and the APB FSM go to BUSY.
- Rules BR-12-05, BR-12-07, BR-12-08: For ERR-003/004/005, does PREADY assert in the same cycle as the TL-UL d_valid response is accepted, or one cycle later? The quotes say 'with PREADY' without timing.
  - **Answer from the text:** PREADY comes one cycle after the response is accepted. The response is checked and loaded into the response flops at the end of the response cycle (A2), and PREADY, PSLVERR and PRDATA are output in the next cycle (A3). The latency is the same as OP-001 and OP-002.
- Rules BR-12-09: For ERR-006, what is the expected behavior if a response arrives after reset abandons the transfer?
  - **Answer from the text:** The transfer is abandoned and no APB completion is sent after reset release. A late response then finds no accepted request and is discarded as an orphan.
- Rules BR-13-01, BR-13-02, BR-13-03: Is each access-phase length an exact value or only a maximum? The quotes say 'Target / limit'. Is the access phase counted from PSEL/PENABLE assertion?
  - **Answer from the text:** The lengths are exact hard requirements: 3 cycles, 2 cycles and 1 cycle for the stated conditions. The Access phase starts in the cycle after Setup (PSEL=1, PENABLE=1) and lasts until PREADY is high.
- Rules BR-13-04, BR-13-01, BR-13-02, BR-13-03: Is the minimum transfer interval an exact period or only a lower bound? How does it relate to the access-phase lengths? The 4, 3 and 2 cycle intervals seem to be the access phase plus one setup cycle, but this is not stated. Also, 'As above' leaves the condition unclear.
  - **Answer from the text:** They are minimum intervals, measured from Setup to Setup. 4 cycles is S plus the 3 Access cycles, 3 is S plus 2 for a same-cycle response, and 2 is S plus the 1 local-error Access cycle. The same intervals apply when PSEL stays high, with no idle cycle added by the bridge. The conditions are the stated ones: prompt device, same-cycle response, local error.
- Rules BR-14.3-01: The rule text for BR-14.3-01 ends with a dangling 'WHEN lint' fragment. Is there a condition that was cut off? Also, does the waiver cover only the five listed unused inputs, or may other waivers exist?
  - **Answer from the text:** The spec sentence is complete and has no cut-off condition. The lint waiver covers the five unused inputs i_apb_pprot, i_tlul_d_param, i_tlul_d_size, i_tlul_d_sink and i_tlul_d_user. The spec also says the RTL complies without local exceptions.
- Rules BR-14.1-03, BR-14.1-04, BR-14.1-05: BR-14.1-05 repeats part of BR-14.1-04 and BR-14.1-03 but leaves out the FSM names and the reset requirement. Should verification treat it as a separate rule or as the union of those rules?
  - **Answer from the text:** The spec has one list of the coding-baseline items that matter most, covering one module per file, structural top, ANSI ports, naming, FSM names, PARA_ comments, length limits and async reset on every flop. Treat the rule as that full union.
- Rules BR-15.2-01: BR-15.2-01: the 'listed outputs' are not enumerated in the quote; which outputs are reset to 0 and is d_ready the only exception?
  - **Answer from the text:** The reset outputs are o_tlul_a_valid, o_tlul_d_ready, o_apb_pready, o_apb_prdata, o_apb_pslverr, o_tlul_a_opcode, o_tlul_a_address and o_tlul_a_data, all 0. d_ready is not an exception in reset, since it is 0 there and becomes 1 after release. The constant tie-offs (a_param, a_size, a_mask, a_source, a_user) hold their constant values.
- Rules BR-15.3-12, BR-15.3-02, BR-15.3-05: BR-15.3-12 / BR-15.3-02 / BR-15.3-05: channel A stability checks apply only while a_valid is 1, but constants such as a_size and a_mask may be undefined when a_valid is 0; should SVA-005 be qualified by a_valid?
  - **Answer from the text:** The constant fields are tie-offs that never change after reset, so they are defined even when a_valid is 0. Stability checks apply only while valid is high and ready is low, and the REF-005 checkers sample channel A only while a_valid is 1.
- Rules BR-16-03: What exactly does 'idle state after reset' mean for the IP (which signals or state values), and is it already covered by the reset behaviour rules elsewhere in the spec?
  - **Answer from the text:** Idle after reset means both FSMs are in ENUM_ST_IDLE and the listed flops (reg_a_valid, reg_d_ready, reg_pready, reg_pslverr, reg_prdata, reg_a_rd, reg_a_addr, reg_a_data) are 0. That is the same state already given in the reset section.
- Rules BR-16-01: How will scan eligibility be checked (lint or DFT tool flow), since simulation cannot verify it?
  - **Answer from the text:** Scan eligibility is checked statically with lint and a scan rule check (TEST-018), not by simulation.
- Rules BR-20-04, BR-20-05: Does the misaligned-address PSLVERR in DEC-001 apply to reads as well as writes? The quote only mentions 'every misaligned address'. Is PRDATA 0 on those errors?
  - **Answer from the text:** Yes. The misaligned-address rule covers reads and writes. The error response is PSLVERR=1 with PREADY, no TL-UL request, and PRDATA=0.
- Rules BR-20-11: For 'o_tlul_d_ready is 1 from the first edge after release', is it first observed high after that edge (flop with D=1) or already high before it? Is it still 0 during that first cycle?
  - **Answer from the text:** o_tlul_d_ready is a flop that resets to 0 with D=1. It is 0 in reset and until the first clock edge after release, and it is high after that edge. It is not already high before that edge.
- Rules TL-T4.1.3.4-02, TL-T4.1.3.5-06, TL-T4.1.3.4-03: Hosts never use non-contiguous masks, yet devices may or may not error on them. Should the testbench ever drive non-contiguous masks, and what response is expected?
  - **Answer from the text:** Hosts in this project do not use non-contiguous masks, and devices may or may not support them and may assert d_error. For this bridge a_mask is always 4'b1111, so the testbench never needs to drive non-contiguous masks.
- Rules TL-T4.1.3.5-02, TL-T4.1.3.5-03, TL-T4.1.3.5-04, TL-T4.1.3.5-07: Are the illegal-request cases host obligations or device-checked errors? Is d_error mandatory for every violation or only for the listed checks?
  - **Answer from the text:** Devices raise d_error for the listed checked properties (wrong opcode, address/size/mask combinations, non-existent addresses). The remaining basic properties of the TL-UL spec are enforced at design time by assertions with no HW checker, and devices and hosts may add stricter checks. So d_error is mandated only for the listed checks.
- Rules TL-T4.1.3.4-04, TL-T4.1.3.5-02: a_size should be 2 for PutFullData but must not exceed 2 in general. Is a smaller size for PutFullData allowed?
  - **Answer from the text:** a_size should be 2 for a 32-bit PutFullData, but the bus spec allows it to be defined otherwise. Size above 2 is never allowed, and PutFullData must mark all active lanes in a_mask. This bridge always uses a_size=2.
