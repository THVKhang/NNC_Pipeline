## 1. CHK-002 – Output values while reset is asserted (7 fails, one per run, always @0 ps; sim.log:122, sim_runs/*.log)

**Most likely:** B_test_wrong

| Part | Content |
|---|---|
| Specification says | spec/uart_lite_Design_Specification.md:106 REQ-RST-002 "While i_rst_n is 0, the outputs shall have these values: o_txd = 1, o_tx_ready = 1, o_rx_valid = 0, o_rx_data = 0, o_rx_frame_err = 0, o_rx_overrun = 0." Line 104 REQ-RST-001: "When i_rst_n becomes 0, every flip-flop ... shall take its reset value at once". Line 358 ENV-002: "The environment shall hold i_rst_n at 0 for at least 2 cycles of i_clk at the start of a simulation." contract.json:705 (UL-12.1-02): "Applied as a stimulus constraint: every simulation starts with i_rst_n=0 for at least 2 i_clk cycles." The spec does not say what the outputs are at time 0, before any reset event has happened. |
| RTL does | All output flops have an asynchronous active-low reset to the required values: rtl/m_uart_lite_tx.sv:49-52 (o_txd<=1, o_tx_ready<=1) and rtl/m_uart_lite_rx.sv:176-181 (o_rx_valid/o_rx_data/o_rx_frame_err/o_rx_overrun<=0). There are no initial values, so before the first negedge of i_rst_n (or a posedge of i_clk with i_rst_n=0) the outputs hold the simulator's initial value. Verilator 2-state starts them at 0. At t=0 o_txd/o_tx_ready are therefore 0. This matches the CHK-010 fails at 0/20/40 ns, which show the DUT was not reset at the t=0 edge. Every later reset assertion passes: 1416 of 1417 hits pass, and the Python check one time step after each assertion (test_uart_lite.py:192-194) passes in all 20 tests. |
| Test does | Env.start() drives i_rst_n=1 at t=0 (verif/tests/test_uart_lite.py:144) and starts the clock (146). It waits two rising edges (149-152) and a falling edge (158). Only then does it call reset(), which waits another rising edge plus 0.3P and drives i_rst_n=0 (185-189), at about 46 ns. The SVA (verif/sva/nnc_chk_reset.sv:22-24) samples at every posedge with !i_rst_n. At the t=0 posedge the sampled i_rst_n is still the simulator default 0, because cocotb's write of 1 happens in the same time step. The sampled outputs are the un-reset 0 values, so o_txd===1 fails. The expected values come straight from REQ-RST-002. The failure is a time-0 initialisation and race artifact. nnc_tb_top.sv and nnc_cocotb.start_clock are not in this directory, so the exact clock phase at t=0 cannot be confirmed. |
| B_test_wrong | For: The test breaks ENV-002 (spec:358) and the contract's own stimulus constraint (contract.json:705): i_rst_n is set to 1 at t=0 (test_uart_lite.py:144), and the first assertion is at about 46 ns (lines 149-159, 185-189). There is exactly one fail per run, always @0, in all 7 runs (results.json:314-349). The same start-up window also produces the CHK-010 fails at 0/20/40 ns. The checker samples i_rst_n=0 at t=0 only because the port has not yet been written (a Verilator time-0 race). Every real reset assertion later in the run passes.<br>Against: The exact time-0 sampling semantics depend on nnc_tb_top.sv and start_clock, which are not provided. If the harness truly drives i_rst_n=0 at the t=0 edge, the stimulus is momentarily ENV-002-compliant at that edge. |
| C_spec_unclear | For: REQ-RST-001/002 (spec:104,106) describe what happens when i_rst_n *becomes* 0. They do not say what the outputs are at power-up, when i_rst_n is 0 from t=0 with no negedge and no clock edge yet. An async-reset flop with no initial value cannot meet "while i_rst_n is 0" before its first reset event. If the stimulus is fixed to hold reset low from t=0 but the clock still has a rising edge at t=0, CHK-002's preponed sample at t=0 could still see un-reset outputs.<br>Against: ENV-002 makes reset at the start mandatory, and the intent of REQ-RST-002 is clear for every cycle after reset has taken effect. The ambiguity only affects the single t=0 sample. |
| A_rtl_wrong | For: At the t=0 sample the outputs are 0/0 for o_txd/o_tx_ready instead of 1/1.<br>Against: The RTL implements the async reset exactly as REQ-RST-001/REQ-IMP-004 require (m_uart_lite_tx.sv:49-52, m_uart_lite_rx.sv:176-181). Every real reset assertion gives the correct values, both in the SVA (1416 passing hits) and in the Python check one step after assertion (test_uart_lite.py:192-194). The spec does not require power-up values without a reset. |
| Options | Fix test (recommended): in Env.start() (test_uart_lite.py:142-160), drive i_rst_n=0 before start_clock, so the outputs see a real reset before the first rising edge, and hold it for at least 2 cycles as ENV-002 and contract.json:705 require. Also make sure the clock's first rising edge comes after the reset is applied, for example by starting the clock low; that removes the t=0 race. Clarify spec (optional): add a sentence to REQ-RST-002/ENV-002 saying output values are only defined after the first assertion of i_rst_n has taken effect, so the checker has a defined start point. That matches the existing nnc_env.sv ENV-01 assumption. No RTL change is indicated. |

| B_test_wrong | For: The SVA model (nnc_chk_rx.sv:64-68) differs from the spec and from the contract model: it lacks the s(T0-1)=1 condition of REQ-RX-003 (spec:172), contract.json:781 and REQ-FE-003/D-005. The fail period equals H+9N+1 exactly (153 cycles at N=16, 39 cycles at N=4), which is a restart at M+1 on a line that is still low. All fails fall in tests with low lines or stop=0 frames: chk_021 at 311.9-329.2 us, chk_028 at 952.2-1003.8 us, chk_029/regression after error frames (sim.log:57-95). The only RTL-side possibility would be a real missed delivery, but the Python model, which follows the spec, agrees with the RTL in every one of these windows. |
| A_rtl_wrong | For: At the model's V the RTL leaves o_rx_valid at 0.<br>Against: The RTL start rule (m_uart_lite_rx.sv:84) is exactly REQ-RX-003. A second delivery from a constant-low line is forbidden by REQ-FE-003, REQ-ERR-001, REQ-ERR-003 and D-005. The independent Python reference passes on the same stimulus. |
| C_spec_unclear | For: Section 1.2 (spec:17) only says "Start-bit detection on a falling edge". Someone could read 'start bit detected when the line is low'.<br>Against: REQ-RX-003, REQ-FE-003, REQ-ERR-001/003, D-005 and the contract assumption (contract.json:781) all state explicitly that a 1->0 transition is required and that a held-low line gives exactly one frame. |
| Options | Fix the checker model (recommended; this makes it stricter, not weaker). In verif/sva/nnc_chk_rx.sv add `logic mdl_prev;`, set it to 1'b1 in the !i_rst_n branch (so s(R1-1)=1, REQ-RST-010), and update it with `mdl_prev <= i_rxd;` on every non-reset edge. CHK-003, CHK-005, CHK-006 and CHK-009 should all clear together, because they share this model. No RTL change and no spec change is indicated. |
